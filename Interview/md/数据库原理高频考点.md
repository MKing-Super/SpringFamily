# 数据库原理高频考点

## 一、索引与查询优化

### 1. B+树结构

​		B+树是所有数据都存放在叶子节点的平衡多路搜索树，非叶子节点只存键值用于路由。相比 B 树，B+树的叶子节点之间通过双向链表连接，更适合范围查询和全表扫描。相比哈希索引，B+树支持排序和模糊匹配，且磁盘 IO 次数更少。

### 2. 聚簇索引 vs 二级索引

​		聚簇索引的叶子节点直接存储整行数据，一个表只能有一个；二级索引的叶子节点存储主键值，查询时需要回表。覆盖索引是指二级索引的叶子节点已经包含了查询所需的全部字段，无需回表，效率更高。

### 3. 最左前缀原则

​		联合索引按照定义时的字段顺序从左到右匹配，遇到范围查询（>、<、between）会停止匹配。例如索引 (a,b,c)，查询条件 where a=1 and b>2 and c=3 只能用到 a 和 b，c 无法走索引。所以应该把区分度高的字段放在最左边。

### 4. 索引失效场景

​		常见的失效情况包括：对索引列使用函数或计算、隐式类型转换（比如字符串字段传入数字）、like 以通配符开头、or 条件中有非索引列。用 explain 查看 type 字段，如果变成 ALL 或 index 就说明索引失效了。

### 5. EXPLAIN 执行计划

主要看四个字段：

type 从好到差依次是 const、ref、range、index、ALL；

key 表示实际用到的索引；

rows 是预估扫描行数；

Extra 中出现 Using filesort 或 Using temporary 代表需要优化。目标是让 type 至少达到 range 级别。

#### 5.1 type

type 字段（访问类型，从好到差排序）

| 类型      | 含义                                   | 一句话解释                                                   |
| --------- | -------------------------------------- | ------------------------------------------------------------ |
| **const** | 最多返回一行，用主键或唯一索引等值查询 | 命中主键或唯一索引，MySQL 知道最多只有一条匹配，速度最快。   |
| **ref**   | 普通索引等值查询，返回多行             | 用了普通索引且条件是等值匹配，比如 `where name = '张三'`，name 上有索引。 |
| **range** | 索引范围扫描                           | 用了 `>`、`<`、`between`、`in`、`like 'abc%'` 等范围条件，走索引但扫多行。 |
| **index** | 全索引扫描                             | 遍历整个索引树，比全表快一点因为索引通常比数据小，但仍然是扫描全部。 |
| **ALL**   | 全表扫描                               | 没有用到索引，逐行扫描整张表，最慢，必须优化。               |

**记忆口诀**：const 最快，ALL 最慢，目标是至少到 range。

**面试回答示例**：

> type 表示 MySQL 是如何查找数据的，从好到差依次是 const、ref、range、index、ALL。const 是用主键或唯一索引精准定位一行；ref 是普通索引等值匹配；range 是范围扫描；index 是全索引扫描；ALL 是全表扫描。我们日常优化至少要达到 range 级别，最好能到 ref 或 const。

------

#### 5.2 Extra

Extra 常见字段（额外信息，重点看这几个）

| Extra 内容                | 含义                                           | 好坏                   |
| ------------------------- | ---------------------------------------------- | ---------------------- |
| **Using index**           | 覆盖索引，不需要回表                           | ✅ 好                   |
| **Using where**           | 在存储引擎层过滤后，Server 层还要再过滤        | 一般，注意看有没有索引 |
| **Using index condition** | 索引下推，把过滤条件下推到存储引擎层           | ✅ 好（5.6+ 特性）      |
| **Using filesort**        | 文件排序，无法用索引排序                       | ❌ 需要优化             |
| **Using temporary**       | 使用了临时表，常见于 group by、distinct、union | ❌ 需要优化             |
| **Using join buffer**     | 没有用到索引做连接，用了 join buffer           | ❌ 需要优化             |

**重点记两个坏的**：

- **Using filesort** → 排序字段没有走索引，加索引或改 order by 字段顺序
- **Using temporary** → group by / distinct 没走索引，考虑加联合索引

**面试回答示例**：

> Extra 字段里，出现 Using filesort 或 Using temporary 是明显的性能问题信号。Using filesort 说明排序没有用到索引，需要检查 order by 字段是否有合适的索引；Using temporary 说明 group by 或 distinct 操作创建了临时表，通常也是索引缺失导致的。出现 Using index 则是好事，代表覆盖索引，不需要回表。





## 二、事务与并发控制

### 6. ACID 特性

​		原子性靠 undo log 实现回滚；持久性靠 redo log 保证崩溃恢复；隔离性靠锁和 MVCC 实现；一致性是前三者的最终目的。其中隔离性是面试重点，InnoDB 通过不同级别的锁和版本链来保证。

### 7. 事务隔离级别

​		四种级别：读未提交（有脏读）、读已提交（有不可重复读）、可重复读（有幻读）、串行化（性能最低）。MySQL InnoDB 默认是可重复读，并通过间隙锁和 MVCC 解决了幻读问题，所以实际效果接近串行化但性能更好。

### 8. MVCC 原理

​		每行记录有两个隐藏列：事务 ID 和回滚指针。每次更新会生成一条 undo 日志形成版本链。ReadView 记录了当前活跃事务列表，通过比较事务 ID 判断哪个版本可见。可重复读级别下，同一个事务的 ReadView 在第一次查询时生成并复用，所以不会看到其他事务的新增数据。

### 9. 快照读 vs 当前读

​		快照读就是普通的 select，不加锁，利用 MVCC 读取历史版本。当前读是 select ... for update、insert、update、delete，总是读取最新版本并加锁。这也是为什么可重复读下仍然可能出现幻读——当前读能看到新插入的行。



## 三、锁机制

### 10. 行锁 / 间隙锁 / Next-Key Lock

​		行锁只锁住索引记录；间隙锁锁住两条记录之间的空隙，防止幻读；Next-Key Lock 是行锁加间隙锁的组合。InnoDB 的可重复读级别默认使用 Next-Key Lock，但如果索引是唯一索引且查询条件精确匹配，会退化为行锁。

#### 10.1 三个锁分别是什么

**1. 行锁（Record Lock）**

- **锁定对象**：锁住**索引中的某一条记录**
- **特点**：只锁一行，粒度最小，并发度最高
- **触发条件**：对索引列做等值查询且命中唯一索引/主键时，会退化为行锁

**例子**：

```sql
-- 假设 id 是主键
SELECT * FROM user WHERE id = 5 FOR UPDATE;
-- 只锁住 id=5 这一行，其他行不受影响
```

**2. 间隙锁（Gap Lock）**

- **锁定对象**：锁住**两条记录之间的间隙**，或者第一条记录之前、最后一条记录之后的区间
- **特点**：不锁任何具体记录，只锁“空隙”，目的是**防止其他事务在这个间隙里插入新数据**
- **触发条件**：可重复读级别下，对非唯一索引做等值或范围查询，且查询条件不存在时

**例子**：

```sql
-- 假设 age 上有普通索引，当前有 age=10 和 age=20 两条记录
SELECT * FROM user WHERE age = 15 FOR UPDATE;
-- 间隙锁会锁住 (10,20) 这个区间，阻止其他事务插入 age=15 的新行
```

3. Next-Key Lock

- **定义**：**行锁 + 间隙锁的组合**
- **锁定范围**：锁住**一条记录本身 + 它前面的间隙**
- **特点**：InnoDB 可重复读级别下的默认锁策略，既能保护现有记录，又能防止幻读

**例子**：

```sql
-- 假设 age 上有普通索引，当前有 age=10 和 age=20 两条记录
SELECT * FROM user WHERE age BETWEEN 10 AND 20 FOR UPDATE;
-- Next-Key Lock 会锁住：
--   (负无穷, 10] 的前半段间隙
--   [10, 20] 这个区间内的所有记录和间隙
--   (20, 正无穷) 的前半段间隙
```

------

#### 10.2 三句话总结区别

| 锁类型            | 锁什么             | 防止什么                  | 典型场景                           |
| ----------------- | ------------------ | ------------------------- | ---------------------------------- |
| **行锁**          | 单条记录           | 其他事务修改/删除这条记录 | 主键等值查询                       |
| **间隙锁**        | 两条记录之间的空隙 | 其他事务在空隙中插入新行  | 非唯一索引等值查询（查不到记录时） |
| **Next-Key Lock** | 记录 + 前面间隙    | 既保护记录又防止插入      | 可重复读级别的范围查询             |

------

#### 10.3 面试回答模板（3 句话搞定）

> 行锁只锁住单条索引记录，是最细粒度的锁；间隙锁锁住两条记录之间的空隙，防止其他事务插入新数据导致幻读；
>
> Next-Key Lock 是行锁和间隙锁的组合，既锁记录又锁间隙，是 InnoDB 可重复读级别的默认锁策略。如果查询条件用的是唯一索引且能精确匹配到一行，Next-Key Lock 会退化为行锁以提高并发性能。

------

#### 10.4 面试可能会追问的坑

**Q：什么时候间隙锁会升级为表锁？**

> 如果查询没有用到索引，或者索引失效，InnoDB 无法确定要锁哪些行和间隙，就会锁住整个表的所有间隙，实际上相当于表锁。

**Q：读已提交级别下有间隙锁吗？**

> 没有。读已提交级别只使用行锁，不使用间隙锁和 Next-Key Lock，所以会出现幻读。

**Q：间隙锁会导致死锁吗？**

> 会。最常见的场景是两个事务互相等待对方释放间隙锁，比如事务 A 锁住了 (10,20)，事务 B 也想锁同样的区间，就可能死锁。



### 11. 死锁排查与避免

​		用 `SHOW ENGINE INNODB STATUS` 查看最近一次死锁信息，重点关注 LOCK WAIT 和事务持有的锁。常见避免方法：保持一致的加锁顺序、尽量使用等值查询而不是范围查询、缩短事务执行时间。如果业务允许，降低隔离级别也能减少死锁概率。



## 四、性能调优

### 12. 慢查询日志 / 大分页优化

​		开启慢查询日志设置 long_query_time 阈值，用 mysqldumpslow 分析。大分页问题如 limit 100000,10，可以用覆盖索引先查出主键再关联原表，或者记住上一页的最后一条 id 做游标翻页。延迟关联的思路是先用索引快速定位到需要的 id，再用 join 回原表取完整数据。
